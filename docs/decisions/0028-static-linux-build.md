# 0028. A static Linux build with its own Qt: one archive for any distribution

- Status: accepted (2026-10-22), at the user's request; the .deb and .rpm made from the static build the same day (0.2.3), also at the user's request; review fixes in 0.2.4 (file dialogs, `install.sh`, the image and its CI cache)
- Spec items: section 11 (Linux packages with system Qt; AppImage and Flatpak in the second round), section 7 ("on Linux only system packages"), NFR-3

## Context

A build against the distribution's Qt runs only with that Qt. Within Qt 6 the binary compatibility goes forward, so a public-API build survives a Qt update, but since 0.2.1 the program also uses private Qt API (the GNOME window menu, ADR 0026; the xdg-activation token). The Fedora binary needs `Qt_6.11_PRIVATE_API`: a Qt 6.12 update inside Fedora 44 would make dnf hold back Qt or remove markpaste, and on Debian/Ubuntu a .deb would stop starting after a distribution upgrade. The `.tar.gz` of 0.2.0–0.2.1 was the Fedora build and needed exactly Qt 6.11.

The user asked for a build that is as static as possible, with the newest Qt, at the price of size.

## Decision

- **`tools/static/`**: a `Dockerfile` (Debian 12), `build-qt.sh` and `build-kde.sh` build a static **Qt 6.12.0** (qtbase, qtsvg, the client part of qtwayland, linguist tools, qttranslations; the Wayland client itself is part of qtbase since 6.10) and a static **LayerShellQt 6.8.1** into `/opt/qt` of the image. `tools/static/build.sh` (or `build-in-container.sh static`, the CI target `static`) builds Markpaste with it, runs the core and UI tests and packs `dist/markpaste-X.Y.Z-linux-x86_64.tar.gz`.
- **The image** (0.2.4) is named `markpaste-static:<hash>`, the first 12 hex digits of SHA-256 over `Dockerfile`, `fetch.sh`, `build-qt.sh` and `build-kde.sh`: a change to any of them builds a new image instead of reusing an old one (until 0.2.3 an existing `markpaste-static` was reused, so the `rpm` added in 0.2.3 was missing from an older image). Each version and its checksum are written next to its download (CMake and wayland-protocols in the Dockerfile, Qt in `build-qt.sh`, ECM and LayerShellQt in `build-kde.sh`), not as build arguments: a `--build-arg QT_VERSION=…` could never pass the fixed checksums. The steps go from the slowest to change to the quickest, so a LayerShellQt change does not rebuild Qt; `tools/static/sources/` is mounted only while a step runs (`RUN --mount=type=bind`) and does not stay in the image.
- **The Qt features turned off at the source**: since Qt 6.10 the Wayland features are defined in qtbase, so `FEATURE_wayland_server=OFF` (the compositor library) and the wl-shell and fullscreen-shell plugins are switched off in the qtbase step; in the qtwayland step the same switch had no effect, and until 0.2.3 the image built `libQt6WaylandCompositor.a` for nothing. The ivi-shell and qt-shell plugins are off in the qtwayland step.
- **Debian 12 as the base**: glibc 2.36, the binary needs at most `GLIBC_2.35`. It runs on Debian 12+, Ubuntu 22.04+, Fedora 36+, and current Arch and openSUSE Tumbleweed.
- **What stays shared** (every graphical desktop has it, the ABI is stable for decades): glibc, libstdc++, libwayland-client/cursor, libxcb, libxkbcommon(-x11), fontconfig, freetype, libdbus-1. Everything else is inside: Qt, its platform plugins (wayland, xcb, offscreen), xdg-shell, the Adwaita/Bradient decorations, ibus and compose input, the xdg-desktop-portal theme, SVG, the xcb extensions and xcb-util (`libxcb-cursor0` is missing on many desktops), harfbuzz, png, pcre2, zlib.
- **OpenGL is off** (`INPUT_opengl=no`): the program draws with QPainter, Wayland gets shm buffers, so there is no libGL/libEGL dependency. **OpenSSL is loaded at run time**: only the update check needs it, and every distribution has `libssl.so.3`.
- **Plugins**: a static Qt links only its default plugins (xcb, imageformats). `markpaste_import_qt_plugins()` in CMake adds wayland, offscreen (tests), ibus/compose and the portal theme, and drops the formats we never use. Qt reads these settings from the executable target, so every executable calls it: the program, the tests and, since 0.2.4, the tools (`pastetest`, `uipreview`, `bench`; before that they had no offscreen or wayland plugin with a static Qt).
- **File dialogs through the portal** (0.2.4): linking the portal theme is not enough. Qt adds `xdgdesktopportal` to its theme list only in flatpak and snap or when `QT_QPA_PLATFORMTHEME` asks for it, so 0.2.2–0.2.3 ran with Qt's built-in `kde` or `gnome` theme (no plasma-integration, no gtk3 in the static Qt), and the folder dialog was Qt's own widget dialog. `mp::prepareProcess()` (platform/common/Process.cpp) sets `QT_QPA_PLATFORMTHEME=xdgdesktopportal` before `QApplication` when the variable is empty, and `finishProcessSetup()` removes it right after, so a file manager started by "Open folder" does not inherit it. The portal theme takes the desktop's own theme as its base for everything but dialogs (palette, fonts, icons, the tray). A theme the user set (qt6ct) stays.
- **LayerShellQt**: only the static `LayerShellQtInterface`; `Window::get()` installs the shell integration itself, so the plugin and the QML part (it would need QtQml) are cut out of its CMake.
- **The Qt translations** (`qtbase_ru.qm`) go into the resources: a static Qt has no translations directory on the user's machine. `main.cpp` looks in the Qt directory first, then in `:/i18n`.
- **The archive**: `markpaste`, `install.sh`, `share/` (.desktop, icon, AppStream), `LICENSE`. `install.sh` installs into `~/.local` (`--system`: `/usr/local`) and writes the absolute `Exec` path into the .desktop file: KWin lets a program into ScreenShot2 only when `Exec` matches its executable. A running copy is quit and restarted (a replaced file breaks the KWin check, docs/problems.md 2026-10-20). Since 0.2.4: the copies are found by their executable (`/proc/<pid>/exe` is the installed file), so a build elsewhere is left alone; `--quit` runs with `QT_QPA_PLATFORM=offscreen`, so it works over SSH; the script waits up to 5 s for each copy to exit and says so when one does not; with `sudo … --system` it quits every user's copy as that user (`runuser`, the user's `/run/user/<uid>`) and asks to start it again instead of restarting it; a copy is restarted only where `WAYLAND_DISPLAY` or `DISPLAY` is set. `Exec` is quoted and escaped by the Desktop Entry rules when the path has a space or another special character; the icon cache is updated with `gtk-update-icon-cache -t` (the hicolor directories in `~/.local` and `/usr/local` have no `index.theme`, so without `-t` it always failed), and `kbuildsycoca6` refreshes KDE's cache, after an install and after `--uninstall`.
- The `.tar.gz` of the Fedora build is no longer released.
- **The release .deb and .rpm are the static build too** (0.2.3): `build.sh` runs `cpack -G 'DEB;RPM'` in the same container. One package per format, without the release in its name: `markpaste_X.Y.Z-1_amd64.deb` (dpkg-shlibdeps on Debian 12 gives `libc6 (>= 2.35)`, `libdbus-1-3`, `libfontconfig1`, `libfreetype6`, `libgcc-s1`, `libstdc++6 (>= 12)`, `libwayland-client0`, `libwayland-cursor0`, `libxcb1`, `libxkbcommon0`, `libxkbcommon-x11-0`, package names that did not change in Debian 12–13 and Ubuntu 22.04–26.04) and `markpaste-X.Y.Z-1.x86_64.rpm` (rpm's automatic soname dependencies, no `.fc44` dist tag: `CPACK_RPM_PACKAGE_RELEASE_DIST` is off for a static Qt; rpmbuild comes from Debian's `rpm` package). Both add `xdg-desktop-portal`. Since 0.2.4 the Debian-only files of the shared install tree (lintian overrides, the DEP-5 `copyright`, `changelog.Debian.gz`) are `%exclude`d from the .rpm.
- **The system-Qt build stays**: the same CMake builds against a distribution Qt, `build-in-container.sh fedora:44|ubuntu:24.04|ubuntu:26.04|debian:13` makes per-release packages, and CI keeps building them as a check (Qt 6.4 minimum on Ubuntu 24.04) without releasing them (docs/build.md).

## Options considered

- **AppImage with the shared Qt libraries** (linuxdeploy). Simpler: no Qt build. Rejected for now: it needs FUSE, which is not installed by default on several systems (Ubuntu 24.04), and KWin's Exec check does not work with the AppImage mount path that changes on every start.
- **Flatpak.** The spec's second round. The sandbox changes the paths of temporary PNGs and the portal app id; more work than an archive.
- **A fully static binary (static glibc).** Not possible in practice: NSS, `dlopen` of OpenSSL, GPU and input drivers need the dynamic loader.
- **Building libxkbcommon, fontconfig, libwayland statically too.** They read system data (XKB keymaps, font configs, the compositor protocol), and libxcb's users must share one copy; linking them statically only adds version mismatch risks.
- **Debian 11 or Ubuntu 22.04 as the base, for older glibc.** Qt 6.12 needs CMake 3.25 and a C++17/20 compiler; Debian 12 has them (CMake 3.31 is still taken from Kitware for ECM 6.31). Older systems are out of the spec's range anyway.
- **Keeping the per-release system-Qt .deb and .rpm as the release packages.** They break with every Qt update of the distribution (the private API), and five release jobs had to be kept in step. The user chose the static packages, accepting the loss of the Breeze style and fcitx on Fedora KDE as well.

## Consequences

- The binary is 29 MB; the archive, the .deb and the .rpm are 12 MB each. This is above NFR-3 (packages without a bundled Qt up to 5 MB): the bundled Qt is the point of the build.
- Breeze and other system styles and the KDE platform theme are not loaded: the program has its own style anyway (ADR 0019), file dialogs go through the portal theme (only since 0.2.4, see above; 0.2.2–0.2.3 showed Qt's own dialog). fcitx input does not work (its Qt plugin is not built); ibus works.
- Qt security fixes reach users only with a new Markpaste release; the Qt version and its five checksums are changed in `build-qt.sh`.
- The image build (Qt from source) takes 6 minutes on 16 cores, about 30 minutes on a GitHub runner. ~~On every CI run (no layer cache yet)~~: since 0.2.4 CI builds the image with buildx and keeps its layers in the GitHub Actions cache (`type=gha`, scope `static-qt`), so Qt is compiled again only when `tools/static` changes. Measured: the run that filled the cache took 28 min for `static`, the `v0.2.4` tag run with the cache 3 min 20 s. The cache is limited to 10 GB per repository and is evicted after 7 days without use: then the next run builds Qt again.
- Qt 6.12 itself also registers the app id with the portal and warns "Connection already associated with an application ID": we registered first, so the warning is harmless.
- Checked: Ubuntu 26.04 GNOME Wayland (the whole cycle: portal capture, editor, comment, paste into Text Editor, update check over HTTPS, `install.sh` install, update and uninstall); Fedora 44 KDE Wayland (start: KWin ScreenShot2, GlobalShortcuts, ext-data-control); X11 under Xvfb in bare containers of Debian 12, Ubuntu 22.04, Ubuntu 24.04, Fedora 44, Arch, openSUSE Tumbleweed (all libraries found, the program runs). See docs/platform-matrix.md.
